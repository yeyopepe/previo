# Extending an entry already in `inProgress`

Full procedure when `SKILL.md`'s step 0.1 detects that the given `xxxx` already exists at `{changesDir}/inProgress/{xxxx}/`: no new entry is created, the existing one is extended.

1. **Read what's already documented.** Open `{changesDir}/inProgress/{xxxx}/description.md` to understand what was originally asked for, and check whether `design_*.html`, `design_navigation_*.md` or `design_data_*.md` files already exist in that same folder. Don't open `history.md` for this analysis: it's prompt history, not current information (see step 3), and reading it would only spend context without adding anything.
2. **Understand the extension.** Apply the same analysis as `SKILL.md`'s "Steps" step 1 (edge cases, coexistence with what exists, data scope, who can use it, high-level visual definition), but focused on what's now being asked to add or modify **on top of** what's already documented, not from scratch. Propose the reasonable answers yourself and present them to the user for confirmation, same as in the usual flow.
3. **Update `description.md` and `history.md` directly** (without invoking `pv-internal-workflow`, which only knows how to create new entries): add the extension to `description.md`'s **Full description**, making clear what's new relative to what's already written. Separately, append a new `## {today's date} — extension` section at the end of `history.md` with the user's new prompt verbatim, without rephrasing and without touching the file's previous sections (if `history.md` doesn't exist yet because the entry predates this file, create it following `pv-internal-workflow`'s [`history.template.md`](../pv-internal-workflow/history.template.md), leaving the initial session empty or with a note that it wasn't preserved). Don't change the **Code** or **Type** already set in `description.md`. If what's being added involves a flow, a sequence of steps/decisions, or an interaction between states/components from the user's point of view, represent it with one or more `functional`-type Mermaid diagrams (one per use case/user story, same as in "Steps" step 2) obtained from the diagrams skill configured in `framework.skills.diagrams`, along with the essential notes. Keep the same separation `pv-internal-workflow` uses when creating the entry: **Full description** is functional only, understandable by anyone non-technical, without files, functions or classes; if while analyzing the extension (e.g. reviewing existing code for scope doubts) technical information comes up worth noting, add it to **Technical notes** instead of Full description — create that section at the end of the document if the entry didn't already have it.
4. **Update the visual proposal if applicable.** If the extension introduces, modifies, or removes visual elements: invoke (Skill tool) the mockups skill configured in `.claude/pv-context.json`'s `framework.skills.mockups` (if not configured, `pv-internal-mockups-html`), passing it the destination folder and, for each affected element, its description, what should show/change, and the action (`create` for new elements, `edit` for existing `design_*.html` the extension changes) — don't invoke it if the extension doesn't touch anything visual. If it also introduces, modifies, or removes navigation or UI interaction, apply the same rules as "Steps" step 3 — **list the affected navigation/interaction use cases first** (new ones and existing ones that change) before touching any file, and create a new `design_navigation_<description>.md` per new use case or edit the existing one matching each already-represented use case, without mixing two use cases in the same file (Mermaid diagram + notes only for what isn't obvious). If the extension doesn't touch anything visual or navigation-related, leave the existing files as-is.
5. **Update the data definition if applicable.** If the extension introduces, modifies, or removes properties or associated data of something (an object's properties, a table's content, a configuration's fields): create a new `design_data_<description>.md` per new entity/data set, or edit the existing file matching the already-represented entity, adding/modifying rows in its table(s) — it's still a functional definition of what data is needed, never of how it's stored or manipulated. If the extension doesn't touch any structured data, leave the existing files as-is.
6. **Validate with the user whatever changed visually or in the data.** If step 3 added/edited a Mermaid diagram, step 4 created/edited a `design_*.html`/`design_navigation_*.md`, or step 5 created/edited a `design_data_*.md`, present it to the user (same as "Steps" step 4) and ask them to confirm before continuing. If the extension didn't touch anything visual, flow-related, or data-related, skip this step.
7. **Warn if there's a `plan.md`.** If `{changesDir}/inProgress/{xxxx}/plan.md` already exists (i.e. it had already been planned with `pv-how`), tell the user this extension may leave that plan outdated and that `pv-how` should be invoked again on `{xxxx}` to regenerate it.
8. **State the next step.** Confirm that `{changesDir}/inProgress/{xxxx}/description.md` (and, if applicable, its already-validated `design_*.html`/`design_navigation_*.md`/`design_data_*.md`) are updated with the extension, and remind them that to plan/implement, `pv-how` must be invoked on that same `xxxx`.
